### Fixed

- `resolve-conflicts` classifies the conflicted paths from what the commit will carry, not from the working tree: `conflict-map.ts` and `check-resolution.ts` read `.config/jig.yaml` (or the file `JIG_OVERLAY` names inside the repository) and the change-area catalog from the git index (following the symbolic links the index holds, with `/` the only path separator) and every attribute (classification, the conflict-marker scan of staged changes and the reconstruction of git's automatic merge) from the index's regular `.gitattributes` files (`git --attr-source`), which raises the skill's minimum Git version from 2.40 to 2.41. A path's conflict markers are looked for at the size git wrote them with, as well as at the size the index declares. A filename that holds a literal backslash, a link retargeted only on disk, an untracked or ignored `.gitattributes` file, and a staged link named `.gitattributes` no longer let a resolution pass that the committed catalog or attributes would reject. A change to the configuration or the catalog takes effect once it is staged. `check-resolution.ts` no longer reports a declaration whose working tree differs from the index, since the working tree decides nothing. A relative `JIG_OVERLAY` is taken from the working directory, as every other configuration reader takes it, and a configured path that names a directory, or ends in `/` after a file, cannot be read. While `.config/jig.yaml` itself is unmerged, `conflict-map.ts` still records the conflicts and marks the map incomplete, so `check-resolution.ts` refuses until the file is staged and the conflicts are mapped again.
