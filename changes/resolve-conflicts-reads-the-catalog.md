### Added

- `resolve-conflicts` reads the `generated:` entries of the change-area catalog (`drive.change_areas_catalog`): a conflicted path listed in an entry's `outputs` is mapped as a generated file and regenerated with that entry's `command`, so a generator declared in the catalog is not copied into `resolve_conflicts.generated`. A path is classified by `resolve_conflicts.generated` first, then the catalog, then the built-in lockfile table. Catalog `outputs` are literal file paths, matched exactly. A catalog entry with no `command`, one whose `outputs` are not literal file paths, and a catalog that cannot be read are reported as warnings by `conflict-map.ts` instead of being skipped; in the last two cases `check-resolution.ts` refuses until the map runs again and reads every entry. Running `conflict-map.ts` again classifies every mapped path afresh, a staged one included, and clears a recorded decision whose path's class or regeneration command has changed. `check-resolution.ts` classifies every mapped path again from the configuration and catalog as they stand when it runs, and refuses a path whose class or regeneration command differs from the map's until the map runs again. It also refuses while the configuration, the catalog (or the file a link to it resolves to) or a `.gitattributes` file differs between the working tree and the index, whatever its assume-unchanged or skip-worktree flag and whether or not it is ignored, since the commit carries what is staged; after obligation commands run, it reads the catalog again. A path keeps the conflict-marker size it was first mapped with for the whole operation, and the check also looks for markers of the size its attribute gives at check time. The snapshot's `regenerate.source` can now be `catalog`, and the snapshot records `catalogIncomplete`.
