## Executive summary

Execa is a small, mature, single-maintainer-led open-source library with
excellent mechanical quality gates and essentially no written delivery
process. Every check it has runs in CI (lint, type checks, tests across nine
OS/Node combinations, a strict link checker for its documentation); nothing
at all runs before push (no git hooks), and nothing about how the project is
maintained — contribution flow, review, release — is written down anywhere
in the repo. There is zero AI-agent scaffolding (no instruction files, no
glossary, no rules), which for a 2016-era library is expected rather than
negligent. The documentation is unusually good, but it is *product*
documentation; the governance around it is one link-integrity gate plus
convention. The highest-leverage moves, in order: write the one instruction
file that tells an agent (or new contributor) what the gates are and how the
project works (M0 Lite — the raw material already exists in `package.json`);
make the currently fragile lint/link gates structurally reliable and decide
what "advisory" coverage is for (M1); and codify the practiced-but-unwritten
contribution and release process (M4 Lite). Most Jig modules beyond
that are expected-absent for a repo of this shape and should not be pushed.

## Gap analysis (ranked: leverage × effort)

### P1-1 One instruction file (agents and humans currently infer everything)

- **Finding**: the expected workflow (`npm test` = `xo` lint + `ava`/`c8`
  unit + `tsd`/`tsc` type checks) exists only as `package.json` scripts;
  style is delegated wholesale to `xo` defaults plus a ~30-rule inline
  override block (`package.json:98-129`); no CONTRIBUTING, no agent
  instruction file. A contributor or agent's first feedback comes from CI
  after pushing.
- **Why it matters here**: execa receives outside PRs; every one of them
  re-derives the rules from config, and AI-assisted contributions get no
  guidance at all.
- **Recommendation**: add a ~100-line `AGENTS.md` at root (gate commands,
  ESM/Node-version constraints, `lib/` ↔ `types/` parallel-tree convention,
  docs-nav update rule, pointer to maintainers/review expectations). A
  glossary is likely unnecessary at this vocabulary size — fold the few
  terms (subprocess, piping modes) into the file.
- **Module / maturity target**: M0 Lite.

### P1-2 Make the fragile gates structurally reliable; decide what advisory coverage is for

- **Finding**: lint and the lychee link check run on only one matrix leg
  (`if: matrix.os == 'ubuntu' && matrix.node-version == 26`,
  `main.yml:35-37`) — if that leg is skipped or reshuffled they silently
  stop gating; coverage upload is advisory with no threshold and no
  promotion condition (`fail_ci_if_error: false`, empty-threshold
  `codecov.yml`); required-check/branch-protection state is not in the repo.
- **Why it matters here**: the project's entire enforcement story is CI —
  a structurally fragile CI gate is the whole ladder wobbling.
- **Recommendation**: split lint+lychee into their own always-on job;
  declare the jobs as required checks; either give codecov a patch-coverage
  threshold (promoting it to blocking) or record why it stays advisory.
  Optionally add a `simple-git-hooks` pre-push running `npm test` for
  earlier feedback — small for a repo with no hook manager today.
- **Module / maturity target**: M1 Lite→Standard (partial).

### P1-3 Codify the practiced process (one page)

- **Finding**: review authority, merge rights, npm publish, and changelog
  practice (GitHub Releases) are real but written nowhere in-repo; no PR or
  issue templates.
- **Why it matters here**: bus-factor two; the process lives in two
  maintainers' heads and in repo settings invisible to a clone.
- **Recommendation**: a short `.github/CONTRIBUTING.md` (how to run gates,
  what reviews to expect, how releases happen) plus a minimal PR template
  reminding `npm test`. Optionally a tiny index-completeness check: the
  readme "Documentation" nav (`readme.md:90-118`) is hand-maintained; a
  ~10-line script diffing it against `docs/*.md` is a commit-nothing
  freshness check (lychee catches broken links, not missing entries).
- **Module / maturity target**: M4 Lite (+ M2 Standard for the nav check).

## Drift findings

- **Gate set defined twice, differently**: `npm test` runs lint+unit+type
  everywhere (`package.json:23`), while CI decomposes the same set and runs
  lint on one leg only (`main.yml:36-37`). Deliberate (lint is
  platform-independent) but undocumented — the local and CI definitions can
  drift with no check binding them.
- **Sponsor logo readable as tooling**: CodeRabbit appears in the readme
  sponsor block (`readme.md:26`) with no configured reviewer — a human or
  agent skimming for "what reviews this repo" can (and in our first survey
  pass, nearly did) misread it as wired-in. Cosmetic, but worth knowing.
- No stated-vs-actual contradictions found in the docs sampled; the
  hand-maintained readme nav is currently complete (all 22 `docs/*.md`
  linked — verified by enumeration).

## Recommended adoption sequence

1. **M1** — required-checks + always-on lint/link job (hours); optional
   pre-push hook.
2. **M0 Lite** — `AGENTS.md` (an afternoon).
3. **M4 Lite** — CONTRIBUTING + PR template (an afternoon); optional M2
   readme-nav check (an hour).
4. Stop. M3, M5–M12 are expected-absent or not worth their carrying cost at
   this repo's shape and team size; revisit only if the maintainer team or
   contribution volume grows.
