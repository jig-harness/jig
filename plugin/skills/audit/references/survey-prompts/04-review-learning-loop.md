## Survey 4 — Review architecture and learning loop

Your modules (the answers you return): M7, M8, M9 and M11.

Survey how code review and continuous improvement work.

1. Reviewers in play: humans, bot reviewers (CodeRabbit/Greptile/Copilot/custom), their roles and posture (blocking vs comment-only), and any layering rationale. Count a bot only if a workflow step invokes it on pull requests, or host-side evidence (check runs, reviews or comments by a named app) shows it active. The fit report does not carry recent pull-request activity, so look at it yourself and say which of the three channels (reviews, comments, check runs) you did not check; configuration alone is not enough — a badge or sponsor mention is not a reviewer.
   Host-side evidence has one observation time and one 90-day window. The observation time is the audit time when the audited revision is the current tip of the integration branch, and that revision's commit date for a historical audit (the `--at` option, or a clean checkout of an older commit, whose `HEAD` is then the revision). The population is the pull requests open or merged in the 90 days before the observation time, whichever branch they target. Count only activity timestamped within that 90-day window — a review submitted, a comment posted, or a check run completed (or started, if no completion time is recorded) between 90 days before the observation time and the observation time itself; older activity on a long-open pull request or activity after the observation time establishes neither current use nor absence.
   For each of the three channels, inspect every pull request in that population — never a sample, a single channel, or final merge commits alone. For check runs, inspect every pull-request revision the repository host retains (each pull request's head and any retained test-merge commit, as well as the merge commit when checks run there). Distinguish three states of missing host activity evidence: an **unchecked channel** (a channel not queried, a sample that omitted pull requests, a lookup that skipped available pull-request heads or retained test-merge commits, or an unreadable query); **routine turnover of ephemeral intermediate revisions** (such as test-merge commits replaced by a merge or squash commit on merge, or superseded force-pushed revisions); and **materially unretained host history** (where the host no longer retains the surviving channel records for pull requests in the 90-day population, such as check runs outside the host's retention window or pull requests whose head revision is no longer readable on the host). When all three channels were checked for every pull request in the population and the surviving records for their exposed heads and merges remain retained, routine turnover of ephemeral intermediate revisions does not make the census incomplete: that surviving record is sufficient to establish the active reviewers (or `absent` when none appear), and you preserve the observed results and qualify the evidence with the unretained intermediate revisions rather than calling them a skipped check or stopping the audit.
   When examined, with no automated reviewer M7's reviewer criteria score `absent`, never
   `expected-absent` (a draft's unexamined criteria stay as they are): any repository can add one. Always preserve confirmed observations from checked-in wiring and checked channels, and judge evidence completeness per criterion against that criterion's scope for any unavailable evidence that could still change its exact rung: an unchecked activity channel, materially unretained host history that could hold a hosted reviewer's trace, or inaccessible governing evidence about a confirmed reviewer (its configuration, starting posture, written precision bar, promotion gating, runtime, prompt, or active policy source, shadow-testing path, or host enforcement — for example, hosted app settings or branch-protection and ruleset rules visible only to an administrator). Without confirmed wiring or host activity, an unchecked channel or materially unretained host history bars concluding `absent` or recommending installation; even with one confirmed reviewer, missing activity evidence can still hide another hosted reviewer and inaccessible governing evidence can still change a confirmed reviewer's own rung (or whether it is secret-bearing or merge-relevant), so either bars settling any reviewer criterion (including those that apply to every active, secret-bearing, or merge-relevant reviewer) unless confirmed observations already fix its exact rung. Try to close any unchecked channel or readable gap before synthesis. If unavailable evidence of any of those kinds could still change the exact score of a criterion the draft requires an answer for (inside the target, or opened by `--examine-all`; never one already marked `not-examined`), do not guess a score: preserve and report the independently established observations, leave that criterion unresolved, and stop to report the audit incomplete, naming the criterion and the unavailable evidence (unchecked channel, materially unretained host history, or inaccessible reviewer configuration or enforcement). Only where confirmed observations already fix the criterion's exact rung — so the unavailable evidence can neither raise nor lower it (for example, a confirmed in-scope reviewer is already proven `absent` from readable evidence, fixing a weakest-part score at `absent` — never merely failing a higher pass bar such as `advisory` or `convention` where an unseen reviewer could still lower the score to `absent`, and never guessing `absent` for a confirmed reviewer whose unreadable settings could satisfy the criterion) — may you record that score and note the unavailable evidence in the evidence instead of stopping. 2. Review routing: are mandatory review requirements selected by change type? Mechanically or by convention?
3. The comment-resolution loop: is addressing review feedback codified (a closed
   set of terminal states, human-in-the-loop
   ([HITL](https://github.com/jig-harness/jig/blob/main/GLOSSARY.md)) boundaries, thread-resolution mechanics)? Note
   specifically whether a finding whose code is *gone* has anywhere to go other
   than "rejected", and whether the terminal state is **declared** by the author
   in a machine-readable anchored form or **reconstructed from prose** later —
   including what happens to a reply the tooling cannot classify.
4. The review loop over rounds: what ends it? Look for a stop condition that
   distinguishes "no open threads" from "a reviewer has not reported yet", and
   that re-checks the PR is still open each round. A loop driven by a person
   eyeballing the thread list counts as convention, not mechanism.
5. Measurement: is review quality measured at all (missed-defect tracking, vendor parity, eval fixtures, telemetry)?
6. Learning loop: when a reviewer (or gate) misses a real defect, does anything systematic happen? Look for miss taxonomies, regression fixtures, checklist growth, retrospective flows. Is reflection triggered by an *observable* (a round-count threshold, say) or by the author remembering — and does its record carry the measurement that triggered it? Say whose habit it is: turned on in a person's own configuration (with Jig's plugin, the user layer `~/.jig/jig.yaml`, which you can only learn by asking) or in the repository's, which turns it on for everyone working there.
